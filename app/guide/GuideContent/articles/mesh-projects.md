## Mesh — карта совместной работы {#overview}

Project Mesh объединяет задачи, компьютеры, repositories и правила проекта. Его задача — сохранить понятную структуру работы, когда несколько coding agents участвуют в одном результате. Открывая Mesh, вы видите не просто список окон чата, а связь между работой, её исполнителями и доступными фактами.

В учебном **GrantTap Lab** одна Task добавляет фильтр списка задач, другая проверяет поведение пустого списка. Они могут выполняться разными провайдерами, но относятся к одному проекту и согласованным repository bindings. Если один агент уже работает с модулем, другой может увидеть соответствующее намерение и избежать лишнего пересечения.

Mesh не означает общую память без границ, доступ ко всему диску или автоматическое объединение любых похожих папок. Каждый Project остаётся отдельной областью координации и разрешений.

## Account, Project, Task, Execution {#model}

| Уровень | Устойчивый смысл |
| --- | --- |
| Account Mesh | Личная сеть устройств и компьютеров, вход через passkey |
| Project Mesh | Область работы, repositories, участников и Governance |
| Task | Стабильная человеческая единица работы |
| Execution | Конкретная native session одного провайдера на одном компьютере |

Одна Task может получить несколько executions: например, начаться в Claude Code и продолжиться в Codex. Заголовок Task остаётся полезным человеку, а original native conversations сохраняют собственные идентичности и историю.

Дочерние агенты отображаются внутри родительской Task как вложенные execution conversations. Они не являются Skills и не должны засорять основной список независимыми root Tasks. Подробнее о навигации — [Task и Execution](/guide/task-execution).

## Репозитории и рабочие папки {#repositories}

В Mesh / Repositories можно перейти от проекта к опубликованным repository identities и связанным chats. Один Mesh способен включать несколько repositories; один репозиторий может иметь разные checkouts. Приложение сохраняет исходные маршруты и права, даже когда помогает найти связанную работу.

Имя папки не доказывает Git identity. Если сведения отсутствуют или конфликтуют, это должно быть отмечено. Workspace без подтверждённого Git также не превращается автоматически в проверенный repository.

В учебном проекте сначала выберите один репозиторий с небольшим checkout. Проверьте branch, owning computer и текущую Task, прежде чем добавлять вторую рабочую папку. Это упрощает чтение [Graph и Health](/guide/graph-health) и предотвращает путаницу с одинаковыми относительными путями.

:::note Связь не объединяет доступ
Два linked Project могут показывать отношения между repositories, но остаются отдельными access scopes. Их ключи, membership и grants не сливаются только потому, что проекты связаны.
:::

## Что видят агенты {#agent-context}

Поддерживаемый scoped Mesh context содержит bounded сведения: владельцев задач, зависимости, claims, вопросы, ответы и относящиеся к работе события. Он не должен рассылать всем агентам полные transcripts и скрытые рассуждения соседних conversations.

Caller attribution проверяет execution, которая действительно сделала вызов. Знание чужого Task ID не даёт агенту право действовать от его имени. Изменение ownership не является произвольной командой модели: оно связано с проверенным результатом runtime и handoff receipt.

Техническое согласование и advisory conflicts остаются внутри Mesh. Product, business, security, destructive решения, неразрешённые конфликты и failed handoff используют [Needs You](/guide/now-tasks). Так интерфейс сохраняет роль человека там, где нужен выбор, а не требует ответа на каждый технический обмен.

## Claims и пересечения работы {#claims}

Claim — ограниченное по времени заявление о намерении работать с ресурсом. Например, Task сообщает, что собирается менять `src/tasks.ts`. Это помогает другому агенту заметить пересечение до merge.

Claim не доказывает, что файл уже изменён, и не является filesystem lock операционной системы. У него есть срок действия. Одинаковый `src/tasks.ts` в двух разных repositories не означает конфликт. У другого checkout того же repository может быть coordination warning. Сравнение путей учитывает сегменты: `src/tasks.ts` и `src/tasks.ts.bak` — разные ресурсы.

В GrantTap Lab можно показать два учебных намерения для одного модуля, затем объяснить, кто продолжает работу и кто освобождает claim. Не стоит выводить из такой карточки, что агент уже внёс правку: результат проверяется отдельно через [Files и историю](/guide/audit-evidence#levels).

## Перенос задачи и новый владелец {#handoff}

[Handoff](/guide/handoff) продолжает ту же Task в новой execution. Capsule описывает цель, решения и Git facts; отдельно подготовленный перенос сохраняет доступный видимый контекст разговора для destination. Это не копия всего диска и не перенос скрытых рассуждений.

Если source checkout содержит uncommitted changes, они остаются на исходном компьютере, а destination начинает с последнего commit. Интерфейс предупреждает об этом. Явно выбранный checkpoint позволяет включить такие изменения в отдельный commit; push требует своего подтверждённого выбора.

Только проверенный destination receipt меняет ownership. Старую execution после передачи нельзя считать текущей лишь потому, что provider продолжает сообщать о ней. **Open destination** открывает новую работу. **Continue anyway** в старом чате означает параллельную ветку и требует предусмотренного подтверждения компьютера.

## Где находятся правила и знания {#navigation}

В [Governance](/guide/governance) задаются действия проекта; в [Members / Computers](/guide/members) — люди, devices и grants; в [Knowledge](/guide/knowledge-context) — явно записанный контекст. Graph и Health показывают полученные repository reports, а не выдуманную структуру по одному названию.

Для быстрого возвращения используйте [Now и Tasks](/guide/now-tasks). Если компьютер offline, сохранённая информация остаётся полезной, но её свежесть и возможность выполнить новое действие проверяются отдельно. Читайте [offline storage](/guide/offline-storage), чтобы понимать, что именно уже находится на устройстве.
