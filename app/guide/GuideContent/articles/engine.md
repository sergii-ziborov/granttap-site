GrantTap Engine — отдельный компонент компьютера, который обслуживает поддержанные проектные правила, журнал вызовов, память и анализ репозиториев. Это не новая модель, не приложение для телефона и не ещё один coding provider. Он помогает связать наблюдаемую работу с конкретным Project, Task, репозиторием и ревизией. Эта глава объясняет, когда Engine действительно нужен и как отличить его отсутствие от проблемы связи.

## Четыре компонента рядом {#components}

| Компонент | Основная работа | Что важно различать |
| --- | --- | --- |
| Apple app | Показывает задачи, принимает решения, сохраняет полученную историю | Не исполняет локальный код компьютера вместо provider |
| GrantTap MCP и helper | Принимают операции, связываются с CLI, hooks, relay и локальными сервисами | Их доступность не подтверждает готовность Engine |
| GrantTap Engine | Поддержанные policy, Memory, Invocation journal и аналитика | Его готовность проверяется для нужного компьютера и функции |
| Coding provider | Выполняет ход модели и собственные инструменты | Имеет отдельный аккаунт, разрешения и нативную историю |

Основной Mac-клиент использует установленный MCP через авторизованный локальный мост. Он не содержит внутри sandbox второго machine runtime. Поэтому сначала проверяйте [установку MCP](/guide/installation) и [локальный доступ Mac](/guide/mac-app), затем состояние дополнительных возможностей Engine.

## Нужен ли Engine именно для вашего действия {#capabilities}

| Действие | Роль Engine | Если свежего Engine-ответа нет |
| --- | --- | --- |
| Каталог чатов, вопросы и доставка | Основной маршрут обслуживает MCP/helper | Возможности связи проверяются отдельно; отсутствие анализа не означает потерю pairing |
| Новый анализ Graph и карты кода | Выполняется на компьютере с подходящим Engine | Старый отчёт может остаться читаемым, новый не объявляется готовым |
| Knowledge: запись в Memory | Подтверждает запись и её идентичность | Save не должен сразу превращаться в Recorded |
| Runtime Invocation history | Engine владеет долговременным журналом | Показывается недоступность или явный пробел, а не выдуманная история |
| Project Governance | Поддержанный hook обращается к local policy | Поведение зависит от точного маршрута и ранее подтверждённой политики |
| Cortex Loom | Готовит пакет разрешённых проектных сведений | Loaded, Degraded, No report и Prepared имеют разные значения |

Weavatrix и Cortex Loom — библиотеки Engine, а не установленные MCP-серверы или Skills. Не ищите их как отдельные coding providers. Для понимания результата используйте [Graph и Health](/guide/graph-health), [Knowledge](/guide/knowledge-context) и [Runtime](/guide/audit-evidence).

## Обычная установка и фоновая подготовка {#managed-install}

Штатная команда настройки существует в установленном CLI:

```bash
granttap setup
```

Это действие настройки, а не только диагностика: оно может устанавливать или исправлять поддержанные интеграции и helper. Выполняйте его на компьютере, который намеренно подключаете, следуя [установке](/guide/installation). Оно не является командой для получения ответа от модели.

Для поддержанной платформы MCP выбирает закреплённый в своём релизе Engine-артефакт. Платформа, размер и SHA‑256 заданы заранее. Загрузка не может выбрать собственную контрольную сумму. Проверенные исполняемые файлы размещаются в отдельных приватных версиях; декларация переключается после проверки. Если подходящего проверенного релиза нет, настройка сообщает ошибку. Из поддержки IPC на платформе нельзя вывести наличие готового бинарного релиза для неё.

Уже настроенный парный monitor может готовить отсутствующий или устаревший managed Engine в фоне. Первое получение каталога не должно ждать этой загрузки. Неудачная подготовка может повториться позднее, не стирая вопросы телефона. Hooks провайдеров сами не скачивают Engine и не запускают анализ репозитория на пути проверки каждого инструмента.

:::note Не меняйте настройки вслепую
Явное отключение Engine и пользовательская декларация исполняемого файла сохраняют приоритет. Повторные переключения переменных окружения не заменяют проверку конкретного компьютера. Настройка runtime-автообновлений также описана [отдельно](/guide/updates).
:::

## Сначала диагностика без переустановки {#readiness}

1. Откройте Devices и нужный компьютер. Убедитесь, что смотрите owning computer задачи.
2. Проверьте MCP/helper и провайдер. При самостоятельной проверке используйте `granttap status` либо `granttap status --json`.
3. В Project откройте **Tools & Skills → Built-in Mesh intelligence**.
4. Нажмите **Open library diagnostics** и выберите нужный компьютер.
5. Сверьте State, версии библиотек, Last checked и сообщённую причину.
6. Для проблемы Graph отдельно проверьте repository binding, ревизию и свежесть отчёта в Health.

Readiness summary CLI полезен для pairing, helper и провайдеров. Он не является универсальным доказательством, что каждый Engine RPC и анализ репозитория исправны. Аналогично, **No Engine library report has reached this Mesh** означает отсутствие полученного отчёта, а не доказанное отсутствие библиотеки на любом Mac.

Не публикуйте весь диагностический JSON без проверки. Для поддержки обычно достаточно версии, платформы, времени, состояния и очищенного кода ошибки. Секреты, prompts, pairing QR и приватные пути не нужны.

## Если используется свой исполняемый файл {#custom-path}

Для подготовленного и проверенного бинарного файла предусмотрен подтверждённый CLI-маршрут:

```bash
granttap setup --engine "/path/to/verified/granttap-engine"
```

Путь в примере — шаблон, его нужно заменить собственным реальным файлом. Это расширенная настройка для человека, который знает происхождение бинарника. Команда проверяет подходящий исполняемый обычный файл и сохраняет декларацию с контрольной суммой; перед запуском supervisor сверяет байты. Самостоятельно вычисленный hash не превращает неизвестную программу в доверенную.

Не смешивайте вручную путь от одного релиза с checksum другого и не копируйте закрытые каталоги чужого компьютера. Для обычного пользователя предпочтительнее managed-подготовка из своего MCP-релиза. Правила [безопасности](/guide/security) и локальная авторизация остаются обязательными.

## Governance при недоступном Engine {#failure-policy}

Состояние Enforced относится к конкретному провайдеру, компьютеру и категории. Оно не означает контроль всех процессов устройства. В реализованном пути известного управляемого Project, если policy-оценка не ответила и runtime помнит её ревизию, действие переводится в **Ask**: требуется решение человека. Это защищает от молчаливого превращения такого сбоя в Allow.

Однако нельзя переносить этот вывод на неподдержанный hook, неизвестный Project, явно выключенную интеграцию или любой сторонний процесс. В этих случаях действуют предусмотренные для маршрута ограничения и обычное поведение GrantTap. Читайте [Enforcement coverage](/guide/governance#coverage) и причину отказа. Не выключайте глобальную защиту ради исчезновения предупреждения.

## Loaded, Prepared и подтверждённый результат {#evidence}

**Loaded** говорит о загруженной библиотеке. **Succeeded** в Cortex означает подготовленный пакет. **Degraded** показывает неполные сведения. Ни одно из этих состояний само по себе не подтверждает, что агент получил пакет, использовал его или правильно изменил проект.

Отсутствующая метрика остаётся Unknown, а частичный граф — Partial. Подтверждение транспортного запроса, tool success и наблюдаемое изменение файла различаются. В учебном проекте последовательно проверьте библиотечный отчёт, одну запись Knowledge и доступный анализ. Дальше переходите к [доказательствам](/guide/audit-evidence), сохраняя фактические границы каждого результата.
