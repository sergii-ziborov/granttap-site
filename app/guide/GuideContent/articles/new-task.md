Новая задача нужна, когда вы поручаете отдельную работу, а не дописываете следующий шаг в существующий разговор. Самый понятный путь — сначала открыть нужный проект, затем создать Task внутри него. Тогда выбор компьютера и рабочей области ограничен известными связями этого проекта, а первое сообщение получает правильный контекст назначения.

Эта глава описывает форму **New Task** на телефоне, её отличие от общего composer и проверку результата создания. Прежде чем пробовать на рабочем репозитории, подготовьте [тестовый проект](/guide/demo-project).

## Выбрать проект до написания поручения {#project-first}

Откройте **Mesh**, найдите нужный проект и внутри него действие создания новой задачи. Проект указан в верхней части формы. Он задаёт область, а не является ещё одним случайным получателем сообщения.

Проверьте, что у проекта есть доступная рабочая область на подключённом компьютере. Одинаковые названия проектов, папок и веток не гарантируют одинаковую идентичность репозитория. Если привязки отсутствуют, сначала разберите [подключение компьютера](/guide/pairing) и [структуру проекта](/guide/mesh-projects).

Не нужно создавать новый Project для каждого поручения. Несколько независимых задач могут относиться к одному проекту, сохраняя собственные цели и исполнения. Отдельный Project полезен для другой координационной области, репозиториев или правил доступа.

## Написать первое сообщение {#first-message}

Поле **Task** содержит само поручение. Оно станет первым запросом новой работы. Хорошее описание отвечает на пять вопросов:

1. **Цель:** какой результат нужен человеку.
2. **Область:** какие файлы или часть проекта относятся к работе.
3. **Границы:** что разрешено менять и каких действий нужно дождаться.
4. **Проверка:** как агент должен подтвердить результат.
5. **Отчёт:** что вернуть вам после выполнения.

Например, для демонстрационного проекта:

```text
Добавь в README раздел «Как запустить пример».
Используй только команды, которые уже есть в проекте.
Не подключай внешние сервисы и не публикуй изменения.
Проверь, что описание соответствует существующим scripts.
В ответе перечисли изменения и выполненные проверки.
```

Описание ограничено 8 000 символами в проверке формы. Длинные исходные материалы удобнее приложить файлом. Текст «сделай всё красиво» не задаёт проверяемого результата; разбей работу на понятные шаги либо приложи пример ожидаемого вида.

:::tip Сначала цель, потом инструмент
Вместо «используй такой-то MCP» объясните результат и допустимый объём. Выбор инструмента не является доказательством, что он применялся или что его использование разрешено политикой.
:::

## Настроить Run on {#route}

Ниже находятся поля **Agent**, **Computer**, **Workspace** и **Model**. Название компьютера и название рабочей области — разные сведения.

| Поле | Что выбрать | Что проверить |
|---|---|---|
| Agent | Доступного coding provider | Он включён и подготовлен на destination |
| Computer | Компьютер выполнения | Он относится к проекту и соответствует его правилам |
| Workspace | Зарегистрированную рабочую область | Это нужный checkout, а не похожая папка |
| Model | Automatic или сообщённую модель | Каталог относится именно к выбранному компьютеру |

Форма сохраняет текст и вложения при смене провайдера или компьютера. Несовместимый model, Effort или прежняя workspace-привязка могут сброситься: после изменения маршрута перечитайте поля. Не предполагайте, что модель с одинаковым именем доступна во всех аккаунтах.

Если проект закреплён за конкретным execution host, список назначения ограничивается этим правилом. Не меняйте закрепление ради одной ошибки связи, пока не поняли последствия для проекта.

## Модель, Effort и разрешения {#options-permissions}

Модель и Effort определяют параметры первого хода. Automatic позволяет использовать выбор провайдера. Уровни усилия берутся из поддержанных возможностей; неподдержанное значение нельзя принудительно выбрать только потому, что оно существует у другого провайдера.

У новой задачи ещё нет старого контекста для перезагрузки. У существующего чата смена модели имеет отдельные последствия для входных токенов, описанные в [главе о чате](/guide/chat#model-effort). Ни высокий Effort, ни дорогая модель не гарантируют правильный результат.

**В проектной форме New Task нет отдельного универсального поля Permissions.** Действуют существующие правила компьютера, проекта и провайдера. После создания изучайте доступные Task controls, если нужно выбрать разрешённый режим задачи. Запись в prompt «разрешаю всё» не заменяет реальную настройку и не отменяет запреты.

Объём доступа, auto-accept и подтверждённая enforcement coverage разобраны в [Governance](/guide/governance). Не выдавайте полный доступ только для того, чтобы кнопка создания стала активной.

## Приложить материал {#attachments}

Используйте **Add images or files**. Перед отправкой откройте preview и проверьте имя, размер и содержимое. Для одного сообщения действуют обычные пределы: до 10 вложений, до 6 MB на файл и до 11 MB суммарно. Подробности сжатия фотографий и поддержанных previews находятся в [Файлах и голосе](/guide/files-voice).

Файл поясняет первое поручение, но не должен содержать реальные ключи или чужие личные данные для учебного примера. Прикреплённый JSON или документ — данные запроса; он не даёт агенту дополнительного системного доступа сам по себе.

## Create Task и подтверждение создания {#create-receipt}

Перед нажатием **Create Task** ещё раз проверьте проект, компьютер, workspace и первое сообщение. Во время операции появляется **Creating Task…**. До подтверждения нативного создания не считайте локально показанный заголовок доказательством, что провайдер уже создал сессию.

Сетевая доставка, создание нативного разговора и завершение первого ответа — разные этапы. В удалённом пути участвует сохраняемая отправка; на компьютере проверяются маршрут и возможность запуска. Нативный идентификатор появляется из реального результата создания, а не угадывается по названию задачи.

Если экран закрылся, проверьте появившуюся задачу, её исходное сообщение и [квитанции доставки](/guide/message-delivery). При неопределённом результате не нажимайте создание повторно вслепую: первая попытка могла уже запустить провайдера. Сначала обновите каталог и проверьте original computer/provider.

## Если создать задачу нельзя {#unavailable}

Форма может сообщить, что нет компьютера, pinned host не подтвердил grant, компьютер не связан с Mesh либо workspace не зарегистрирован. Это разные причины. Сначала устраните указанную причину, сохраняя исходное поручение.

Доступный маршрут также не гарантирует доступный аккаунт модели. CLI может быть не установлен, не авторизован, выключен настройками или остановлен лимитом. GrantTap не должен самостоятельно входить в сторонний аккаунт или выбирать другой компьютер без подходящего решения.

При закрытии непустой формы используйте **Keep editing**, если хотите продолжить, либо явное **Discard task**. Демонстрационный preview формы не создаёт настоящую работу.

## Общая форма и независимые задачи {#parallel}

Общий composer также имеет **New Task** и выбор провайдера, компьютера и workspace. Он удобен для начала разговора, но не заменяет явный выбор проекта в проектном сценарии. Для важной привязки начинайте из выбранного Mesh.

Две отдельно созданные Task — две самостоятельные цели, даже если работают параллельно в одном проекте. **Agents** внутри чата показывает вложенные разговоры провайдера; они не превращаются автоматически в новые корневые задачи. Для продолжения того же поручения пишите в существующий чат, для смены владельца используйте [Transfer to](/guide/handoff).

Завершите упражнение простой проверкой: найдите созданную Task в [Now или Tasks](/guide/now-tasks), назовите её проект и текущее исполнение, откройте первый запрос и проверьте настоящий ответ. Затем переходите к [делегированию и фоновой работе](/guide/delegation).
